# Rule Discovery

## 1. 目标

把施工中发现的稳定经验沉淀成可复用规则，减少以后每个项目、每个会话重新声明约束。规则分类覆盖代码、设计、产品、验证、安全、运维、AI 协作。适合所有新项目默认具备的能力必须回流到本地模板源，不能只留在某个具体项目里。

## 2. 触发信号

1. 同类问题第二次出现。
2. 用户纠正了架构、设计、验证、安全或收尾规则。
3. 施工中发现底层框架规律，而不是单个文件的偶发现象。
4. 从其它项目参考 skill、脚本或文档，需要抽取通用部分并去除专有约束。
5. 发现新项目模板应默认具备某项规则、能力、检查或文档槽位。
6. 发现某个新项目中新增的 skill、脚本、guard、eval 或文档结构适合其它新项目复用。

## 3. 分类

将规则写入 `docs/architecture/rules/` 下的正确分类：

1. `code.md`：架构分层、模块边界、命名、依赖方向、错误处理、复用抽象。
2. `design.md`：视觉系统、交互模式、响应式、可访问性、文案口径。
3. `product.md`：用户路径、验收口径、商业边界、非目标范围。
4. `testing.md`：快检、单测、集成测试、smoke、eval、剩余手测。
5. `security.md`：密钥、PII、权限、日志、文件上传下载、生产数据。
6. `operations.md`：环境分层、部署、回滚、监控、告警、人工门禁。
7. `ai-collaboration.md`：任务分级、上下文读取、收尾、skill、hook、重复失败处理。

## 4. 目标判定

1. 当前项目事实：只服务当前产品、当前技术栈、当前部署环境或当前商业规则，写入当前项目文档。
2. 模板候选：多个新项目都会需要的能力、skill、规则、检查、文档槽位或工作流，先记录为候选通用能力。
3. 模板源回流：候选内容去除项目名称、路径、域名、部署入口、业务协议、历史兼容和专属能力后，交给 `template-feedback` 回流到本地模板源 `/Users/q/Documents/Projects/NewProject`。
4. 复制后的项目不得把自己当作模板源；如果当前工作区无法访问本地模板源，在交付说明中标记“待回流本地模板源”，写清候选内容、证据、去专有化要求和建议落点。

## 5. 沉淀步骤

1. 先判断规则是否跨任务复用；如果只是一次性事实，写入 `docs/progress.md` 或阶段方案，不写入规则库。
2. 检索 `docs/architecture/rules/`，确认是否已有同类规则。
3. 如果已有规则，更新触发条件、动作或验证方式，避免第二套真值。
4. 如果没有规则，按分类新增条目。
5. 每条规则必须写清：
   - 触发条件。
   - 应采取动作。
   - 验证方式。
   - 适用边界。
6. 如果规则可以机械执行，补充脚本、hook、测试或 checklist 的后续任务。
7. 更新后执行 `node scripts/check-template.mjs`。

## 6. 去专有化规则

参考其它项目时，只允许复制：

1. skill 的触发描述结构。
2. 必读、边界、步骤、验证、交付这种通用骨架。
3. 可复跑脚本的设计思想。
4. guard、smoke、eval 的通用判定方式。

必须删除：

1. 其它项目名称、产品名称、域名、路径和部署入口。
2. 其它项目账号、支付、发布、官网、云平台等专属能力。
3. 只因历史迁移存在的临时兼容规则。
4. 不能在当前模板验证的占位命令。

## 7. 交付要求

1. 说明沉淀到哪个分类文件。
2. 说明为什么这是通用规则而不是项目专有事实。
3. 说明是否需要后续脚本、hook、测试或 eval 承接。
4. 说明执行了哪些检查。
5. 若发现模板级候选能力，说明是否已回流到本地模板源；未回流时必须写清“待回流本地模板源”的客观原因和建议落点。
