# 多语言与文案主链

## 1. 适用范围

1. `frontend-app`、`website`、`desktop-client` 等存在用户可见界面的项目必须在业务 UI 施工前补齐本主链。
2. 后端、CLI、库项目如没有用户可见界面，可以明确记录“不适用”，但错误协议、邮件、通知或生成文档一旦面向最终用户即重新适用。

## 2. 基础不变量

1. 用户可见文案使用 JSON locale 词典或当前技术栈等价的结构化资源，不散落为组件、页面和错误分支中的硬编码字符串。
2. 必须冻结 fallback locale、支持 locale、浏览器 / 系统语言解析、缺 key 行为和格式化参数规则。
3. locale 文件必须保持 key 集一致、值非空、UTF-8 可解析；新增可见文案时同一轮补齐全部已支持语言。
4. 语言名称必须按当前界面语言显示，不直接向用户展示 `en`、`de`、`zh-CN` 等内部代码。
5. 产品内容语言、界面语言、输入语言和解释 / 输出语言属于不同概念时，必须在领域契约和 UI 文案中明确拆分。
6. 语言选择、fallback、资源加载和格式化由稳定的 localization owner 承担；页面只通过 key 取文案，不各自判断 locale。

## 3. 项目初始化后必须补齐

1. locale JSON 物理目录与文件格式。
2. fallback locale 与初始支持语言。
3. runtime localization service / provider / hook 的 owner。
4. 浏览器或系统语言归一化映射。
5. 插值、复数、日期、数字和方向性边界。
6. key parity、JSON 解析、缺 key 和用户界面 smoke 的验证入口。
7. 硬编码用户文案扫描的适用目录与允许例外，例如测试夹具、语言学习素材和外部协议原文。

## 4. 验证

1. JSON locale 可使用 `node scripts/check-localization.mjs --dir <locale目录>` 检查解析、空值和 key parity。
2. 当前技术栈必须补充“源码引用 key 全部存在”和“新增用户可见字符串未绕过多语言系统”的机械检查。
3. 至少使用 fallback locale 和一个非 fallback locale 完成关键页面或窗口运行级 smoke。
