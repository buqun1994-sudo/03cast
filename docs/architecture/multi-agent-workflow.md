# 多 Agent 编排协议

## 1. 使用范围

1. 本协议用于需要多个 Agent 协同的只读审查、文档梳理、测试补充或明确分区施工。
2. 多 Agent 是为了隔离任务边界和提高复核质量，不用于绕过人工确认。
3. 单一任务如果会集中修改同一关键文件，优先使用单 Agent 顺序施工。

## 2. 适用场景

1. 只读 review：一个 Agent 负责审查，主 Agent 负责判断是否采纳。
2. 文档梳理：不同 Agent 按目录分区整理，不同时改同一文档。
3. 测试补充：测试 Agent 只补直接相关测试，主 Agent 负责代码实现。
4. 独立模块施工：模块边界、文件范围和验证命令完全独立时可以并行。

## 3. 禁止场景

1. 同一文件大规模并行编辑。
2. 生产部署。
3. 数据库迁移。
4. 密钥变更。
5. 收尾提交。
6. 支付、权限、账号和用户数据规则的最终决策。

## 4. 角色

1. 主施工 Agent：负责实现、整合和最终交付。
2. 审查 Agent：只读 review，不改文件，不提交。
3. 验证 Agent：运行检查、整理失败原因，不扩大施工范围。
4. 文档 Agent：只在明确文档范围内更新索引、方案或记录。

## 5. 任务单元格式

每个 Agent 的任务必须包含：

1. 目标。
2. 允许修改范围。
3. 禁止修改范围。
4. 必读文档。
5. 验证命令。
6. 输出格式。

## 6. 输出格式

1. 目标：本 Agent 实际处理的目标。
2. 范围：实际读取和修改的文件范围。
3. 改动：完成了哪些具体变更。
4. 验证：执行了哪些命令，结果是什么。
5. 风险：仍需主 Agent 或人工关注的点。
6. 未处理项：明确没有进入本任务的内容。

## 7. 合并顺序

1. 先审查方案。
2. 再主施工。
3. 再验证。
4. 最后由单一收尾流程提交。

## 8. 冲突处理

1. 两个 Agent 需要修改同一关键文件时，停止并改为单 Agent 串行施工。
2. 审查 Agent 提出架构风险时，主 Agent 必须先判断是否需要更新方案或文档，再继续施工。
3. 验证失败时，主 Agent 负责定位根因，不把失败状态直接移交用户。
4. 若工作树已有用户改动影响合并，必须保留用户改动并重新定位边界。
