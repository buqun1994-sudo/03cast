# 验证规则

## 1. 默认规则

1. 代码或工程行为变更后，必须主动执行当前环境可完成的最低成本验证。
2. 编译、类型检查和 lint 只能证明基础正确，不等于用户可见闭环已验证。
3. UI、启动、导航、输入、文件读写、登录、支付、部署等行为变化，需要运行级 smoke 或客观阻断说明。
4. 不能为了让测试通过而降低断言强度。
5. 剩余人工验证必须压缩为最小闭环，禁止泛泛要求整体回归。
6. 项目启用多语言后，必须机械检查 locale JSON 可解析、key 集一致、值非空、源码引用 key 存在，以及新增用户可见文案未绕过多语言主链。
7. 触发条件：在保留真实状态的长期设备上运行会进入目标应用进程的集成测试或 instrumentation。动作：为文件、数据库、安全存储、设备身份和测试签名器注入独立命名空间，禁止复用正式运行时单例或默认密钥；测试结束必须清除测试状态并卸载辅助包。验证：执行前后比对受保护正式记录的文件集合与哈希，确认测试记录、辅助包和测试注册为空，再运行正式应用冷启动 smoke。边界：允许整机重置的一次性模拟器或专用测试设备可以采用重置隔离；长期设备不得清除正式数据来补救测试设计缺陷。

## 2. 车机视频黑屏分层验证

1. 出现“有声音、有进度、无画面”时，验证顺序固定为：发送端媒体信息 -> 播放器状态 -> 硬件解码输出 -> 视频缓冲格式 -> `SurfaceFlinger` 合成类型 -> 实体屏幕观察。
2. 普通 SDR 视频用于验证基础解码与显示主链；4K、HEVC、10-bit、HDR 和 DRM 必须作为独立用例，禁止用复杂片源的失败覆盖基础主链结论。
3. 若视频层为 `Device/HWC`，系统截图或录屏可能只记录应用 UI 与黑色占位区域。最终画面验收必须以实体屏幕为准，并用缓冲入队与合成状态作为机器侧证据。
4. 若视频层为 `Client/GPU`，必须先排查窗口层级、透明度、裁剪、变换和厂商私有缓冲兼容性；不得在没有解码失败证据时切换软件解码或修改全局厂商属性。
5. 当前车机内置屏幕仅报告原生色彩模式，`wideColorGamut=0`、`hdr10=0`。HDR 片源即使能够硬解，也必须单独确认色调映射或显示结果，不得把 HDR 异常与已解决的 SDR 黑屏合并处理。

## 3. 全屏任务交接验证

1. 触发条件：Activity、窗口边界、任务 flag、导航或服务绑定逻辑发生变化。
2. 机器级最低验证：`testDebugUnitTest` 必须覆盖交接令牌和纯窗口策略；`assembleDebug` 后安装到目标车机，确认应用进程、`CastService`、TCP `7000`、HTTP `8200` 存在。
3. 运行级动作：在普通 AVC 媒体正在播放时触发浮窗 -> 全屏，记录 `dumpsys activity` / `dumpsys window` 的边界和前台 Activity，并确认全屏独占 provider 被发现且合作歌词层隐藏；再触发全屏 -> 浮窗，确认边界回到 `(660,90)-(1890,900)`、歌词按最新窗口状态恢复、播放位置继续前进、端口未中断；最后关闭窗口，确认进程、服务和端口释放。
4. 失败边界：若目标车机无法由自动输入触发真实按钮，只能把按钮触发保留为最小人工项，但不得以编译通过代替窗口边界和任务状态证据。
5. 适用边界：本验证只证明窗口交接和媒体生命周期，不证明 HDR、AirPlay 镜像色彩或复杂片源兼容性。
