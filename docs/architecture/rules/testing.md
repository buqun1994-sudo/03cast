# 验证规则

## 1. 默认规则

1. 代码或工程行为变更后，先执行当前环境可完成的最低成本机器检查；默认顺序是语法 / 编译检查，再追加本轮直接相关的单元测试。
2. UI、启动、导航、输入和连续操作变更默认不执行运行级 smoke、截图、坐标点击或连续自动化；这些属于用户主验收，由交付者提供完整手测用例。
3. 手测用例必须写清前置条件、操作步骤、每一步预期结果、失败时记录的现象和停止条件，禁止只写“请整体回归”。
4. 只有用户明确要求、进入里程碑 / 发布门禁，或用户报告卡顿、闪退、协议失败需要诊断时，才执行范围收敛的运行级检查；不得把例外检查升级为日常默认门禁。
5. 安装 Debug APK 是可选的交付准备，不等于交互验证。项目若提供 install-only 入口，可在设备连接时执行；启动应用、检查进程 / 服务和真实交互必须由用户手测或显式授权的诊断任务完成。
6. 不能为了让测试通过而降低断言强度；也不能为了证明已经测试而增加与风险无关的自动化步骤。
7. 剩余人工验证必须压缩为本轮需求的最小闭环，并由用户承担真实设备、真实发送端和视觉交互结论。
8. 项目启用多语言后，必须机械检查 locale JSON 可解析、key 集一致、值非空、源码引用 key 存在，以及新增用户可见文案未绕过多语言主链。
9. 触发条件：在保留真实状态的长期设备上运行会进入目标应用进程的集成测试或 instrumentation。动作：为文件、数据库、安全存储、设备身份和测试签名器注入独立命名空间，禁止复用正式运行时单例或默认密钥；测试结束必须清除测试状态并卸载辅助包。验证：执行前后比对受保护正式记录的文件集合与哈希，确认测试记录、辅助包和测试注册为空，再运行正式应用冷启动 smoke。边界：允许整机重置的一次性模拟器或专用测试设备可以采用重置隔离；长期设备不得清除正式数据来补救测试设计缺陷。该条只在此类测试被明确授权时触发。

## 2. 车机视频黑屏分层验证

1. 出现“有声音、有进度、无画面”时，验证顺序固定为：发送端媒体信息 -> 播放器状态 -> 硬件解码输出 -> 视频缓冲格式 -> `SurfaceFlinger` 合成类型 -> 实体屏幕观察。
2. 普通 SDR 视频用于验证基础解码与显示主链；4K、HEVC、10-bit、HDR 和 DRM 必须作为独立用例，禁止用复杂片源的失败覆盖基础主链结论。
3. 若视频层为 `Device/HWC`，系统截图或录屏可能只记录应用 UI 与黑色占位区域。最终画面验收必须以实体屏幕为准，并用缓冲入队与合成状态作为机器侧证据。
4. 若视频层为 `Client/GPU`，必须先排查窗口层级、透明度、裁剪、变换和厂商私有缓冲兼容性；不得在没有解码失败证据时切换软件解码或修改全局厂商属性。
5. 当前车机内置屏幕仅报告原生色彩模式，`wideColorGamut=0`、`hdr10=0`。HDR 片源即使能够硬解，也必须单独确认色调映射或显示结果，不得把 HDR 异常与已解决的 SDR 黑屏合并处理。

## 3. 全屏任务交接验证

1. 触发条件：Activity、窗口边界、任务 flag、导航或服务绑定逻辑发生变化。
2. 机器级最低验证：直接相关的 `testDebugUnitTest` 覆盖交接令牌、一次性全屏任务、标准任务复用、目标 Surface 有效但 renderer 未确认时不退出来源、当前令牌完成时退出回调只执行一次、取消 / 超时恢复来源输出、同一 Holder 不重复提交 Surface，以及 Android 9 厂商 codec 交接策略；商业布局契约测试覆盖重型设置 `ViewStub` 与二维码按需生成，`assembleDebug` 通过；新增 Android Framework 调用时还必须运行 `lintDebug` 并确认改动路径没有 `NewApi`。如需把 APK 放到车机，使用 install-only 入口，不启动应用。
3. 用户手测用例：在普通 AVC 媒体播放时触发浮窗 -> 全屏，确认按钮响应速度恢复到既有基线，窗口从 `(660,90)-(1890,900)` 进入 `(0,0)-(1920,1080)`；再触发全屏 -> 浮窗，确认边界回到 `(660,90)-(1890,900)`、播放位置继续、端口未中断、进程不退出、背景无全屏投屏残影且没有“无法切换窗口”提示。Android 9 厂商 codec 在新 Surface 上释放 / 重建时允许出现短暂黑屏和有声无画的首帧等待；当前验收以不中断、不报错、不残留旧画面为准，不把这段已知等待判定为播放失败。连续往返不得产生重复窗口、网络重连或不可恢复黑屏，最后关闭窗口，确认广播停止。服务尚未绑定时切换控件应不可操作，绑定后也不得自动执行之前的旧点击。
4. 只有用户明确要求窗口诊断时，才追加 `dumpsys activity` / `dumpsys window`、进程和端口观测；若用户报告卡顿或闪退，按现象收集日志，不提前运行整套 smoke。
5. 适用边界：本验证只证明窗口交接和媒体生命周期，不证明 HDR、AirPlay 镜像色彩或复杂片源兼容性。

## 4. 交付格式

1. 每次代码交付必须列出实际执行的机器检查和结果。
2. 每个用户可见行为变更必须附最小完整手测清单，不以“请自行验证”替代步骤和预期。
3. 未执行运行级检查时，说明“由用户手测”或具体客观阻断；不把未执行项写成通过。

## 5. VPN 共存下的局域网投屏验证

1. 触发条件：车机启用了第三方 VPN，且本轮改动涉及局域网地址选择、DLNA / SSDP 监听或网络媒体连接。
2. 机器级最低验证：运行网络选择器单测和 `assembleDebug`；安装后在目标车机检查 `wlan*` / `eth*` 与 `tun*` 地址、`7000` / `8200` 监听归属，并用 SSDP 探测确认描述地址指向物理接口。局域网媒体与图片连接应使用选中的物理 `Network`，公网媒体沿用系统默认网络；该判断通过代码路径与连接日志复核，不以端口检查替代播放结论。
3. 用户手测用例：保持免流 VPN 开启，启动 Debug“03投屏”，在同一局域网手机的抖音和哔哩哔哩中搜索“03投屏”；两者都应出现且可建立一次视频播放。停止投屏后重新搜索一次，确认“03投屏”仍可发现；发现、权益、配置、支付、接收器进程、窗口和 DLNA / AirPlay 监听不得因 VPN 启停被重启。若失败，记录手机应用、VPN 开关时刻、物理网络断开 / 恢复时刻、车机画面状态和 `adb logcat -s LanAddressMonitor CastReceiverRuntime DlnaRenderer GenaEventPublisher NetworkMediaPlayer PhysicalNetworkDataSource`。
4. 通过标准：VPN 只能改变其自身路由；物理局域网发现、描述地址、网络视频策略、商业链路和既有 AirPlay / DLNA 会话保持可用。该用例不能由 Debug 安装成功或编译通过代替。
