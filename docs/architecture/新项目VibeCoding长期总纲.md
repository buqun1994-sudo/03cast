# 新项目 Vibe Coding 长期总纲

## 1. 文档定位

1. 本文是新项目模板的顶层工作法，用于指导新产品、新模块、新工具、新服务和新客户端从第一天建立稳定 AI 协作底座。
2. 本文不替代具体项目需求；真实产品事实应写入 `docs/product/产品需求基线.md` 和 `docs/architecture/项目长期总纲.md`。
3. 本文只保留跨项目通用原则，不预设任何公司、云平台、支付渠道、账号体系、发布平台或官网主链。
4. 目标是让后续项目的 prompt 越来越轻，项目 harness 越来越稳，用户只在真正需要判断的地方介入。

## 2. 核心原则

0. 先初始化，再施工：
   - 复制模板后的仓库默认处于 `INIT_REQUIRED`。
   - 第一轮必须执行 `project-bootstrap` 或 `node scripts/init-project.mjs`。
   - 初始化前不得把模板态文档、blueprints 或通用能力索引当作项目事实。
1. 成长性：
   - 新项目必须能从每次施工中积累规则。
   - 代码、设计、产品、验证、安全、运维和 AI 协作规则必须分类沉淀到 `docs/architecture/rules/`。
   - 新施工必须先参考已沉淀规则，再决定是否新增、更新或废弃规则。
   - 日后施工中发现适合所有新项目默认具备的能力、skill、规则、检查或文档槽位，必须先记录为候选通用能力，去专有化后回流到本地模板源 `/Users/q/Documents/Projects/NewProject`。
   - 复制后的具体项目不能把自己当作模板源；项目专有事实留在当前项目，跨项目通用能力才回流模板。
2. 基建优先：
   - 从领域模型、数据契约、模块边界、验证入口和运行护栏往上做。
   - 通用能力先抽象成稳定主链，再接具体页面、命令、按钮、脚本或适配器。
   - 不允许东一块西一块复制逻辑，也不允许主动往降级、绕路或弱化验证的方向靠拢。
3. 干净基座：
   - 模板只承载跨项目通用规则。
   - 从其它项目复制经验时，必须去除项目名称、路径、部署入口、业务协议、历史兼容和专有能力。
4. 单一真值：
   - 需求、接口、数据、发布和验证必须各有唯一 owner。
   - 迁移期兼容层必须有 owner、适用范围、测试和退出条件。

## 3. 上下文包

新项目第一天应具备：

1. `AGENTS.md`：每次都必须遵守的硬规则和文档路由。
2. `docs/README.md`：文档索引和任务路由。
3. `docs/architecture/项目长期总纲.md`：项目级系统边界、主链和不变量。
4. `docs/architecture/通用能力索引.md`：能力类型、归属和成熟度。
5. `docs/architecture/Codex规则能力池.md`：需求信号到文档、skill、脚本、guard、eval 的路由。
6. `docs/testing/验证矩阵.md`：不同风险任务的验证入口。
7. `docs/security/安全与密钥边界.md`：密钥、PII、日志、权限和生产数据边界。
8. `docs/progress.md`：当前事实、验证结果、未完成事项和下一步。
9. `.agents/skills/`：高频动态工作流。
10. `scripts/check-template.mjs` 或项目自己的快检入口。

复制模板后的第一天必须先完成：

1. 项目名称。
2. 一句话定位。
3. 项目类型。
4. 源码目录。
5. 最小验证命令。
6. V1 成功标准。
7. V1 明确不做范围。
8. `node scripts/check-project-ready.mjs` 通过。

## 4. 任务分级

1. L0：查询、总结、状态检查。
   - 只读分析，不默认改文件，不默认跑构建。
2. L1：单点文案、小配置、小文档。
   - 定点修改并执行最低成本检查。
3. L2：普通多文件施工、常规 bug 修复。
   - 定位主链，小步实现，跑相关验证。
4. L3：生产、数据、支付、账号、权限、公共协议、数据库、部署、密钥。
   - 先出方案、物理锚点、验证闭环和人工门禁，再施工。
5. L4：重复流程产品化。
   - 把稳定流程沉淀为文档、skill、脚本、hook、测试或 eval。

## 5. Vibe Coding 升级阈值

满足任一条件时，必须从轻量探索升级为工程化流程：

1. 影响真实用户、收入、权限、数据、生产环境或公开承诺。
2. 形成长期主链、公共协议、数据库结构、部署脚本或可复用 SDK。
3. 同类需求预计会出现第二次。
4. 失败后需要排障、审计、回滚或对外解释。
5. 需要多人或多个 AI 接力施工。
6. 已经出现一次因上下文、验证、边界或文档错误导致的返工。

## 6. 反低质量施工

禁止以下做法成为长期方案：

1. 在调用点堆分支，但不修正领域模型或公共契约。
2. 复制已有逻辑，只为了当前页面、当前脚本或当前环境能跑。
3. 隐藏异常、吞掉错误、放宽校验或扩大权限。
4. 用弱断言迁就实现，而不是让验证覆盖真实闭环。
5. 新增旁路入口绕过鉴权、审计、状态机、发布或回滚机制。
6. 把历史兼容写成永久主链，却没有迁移计划和退出门禁。

## 7. 高标准验收

每个 L2 以上任务交付前必须能回答：

1. 目标是否已经从“改什么”上升到“达成什么结果”。
2. 改动是否落在正确层级和主链。
3. 是否避免第二套真值、重复状态机或重复验证口径。
4. 是否有自动验证、运行级 smoke 或清晰客观阻断。
5. 是否把新规则沉淀到文档、skill、脚本、测试或 checklist。
6. 是否把适合所有新项目的新增能力、skill、规则或检查回流到本地模板源，或明确记录为“待回流本地模板源”。
7. 是否能让下一轮 AI 不需要用户重新解释历史就继续。

## 8. 最终形态

1. 用户用最短语言表达真实意图。
2. AI 自动找到正确上下文。
3. 项目底座自动提供规则、工具、检查和护栏。
4. AI 负责执行、验证和整理。
5. 人只在商业判断、架构判断、不可逆操作和最终验收上介入。
6. 每次返工都会反向强化项目底座。
