# Codex 使用流程与 Agentic Engineering 差距分析

## 1. 定位

1. 本文是新项目使用 Codex 的长期工作法说明。
2. 本文不替代 `AGENTS.md`；`AGENTS.md` 仍是每次执行必须读取的硬规则入口。
3. 本文用于解释为什么要建立文档、skills、脚本、guard、测试和 eval，而不是每次只靠 prompt。

## 2. 核心判断

1. Vibe Coding 和 Agentic Engineering 不是是否使用 AI 的区别，而是工程化程度的区别。
2. Vibe Coding 适合探索、低风险原型和可以丢弃的代码。
3. Agentic Engineering 适合生产系统、长期主链、真实用户、公共协议、数据和多人协作。
4. 真正分水岭是验证：
   - tests 验证确定性输出，如编译、类型、单测、集成测试和端到端流程。
   - evals 验证 Agent 行为，如是否读对文档、选对验证、守住人工门禁。
5. Agent = Model + Harness。很多失败不是模型失败，而是上下文、工具、护栏或验证链路缺失。

## 3. 最优单次任务闭环

1. 上下文定位：
   - 读取 `AGENTS.md`。
   - 按 `docs/README.md` 和能力池加载相关文档或 skill。
   - 不把无关历史文档一次性塞进上下文。
2. 方案确定：
   - 简单任务直接施工。
   - 高风险任务先输出方案、物理锚点、验证闭环和不能碰的范围。
3. 定点施工：
   - 优先沿用现有抽象、接口、脚本和验证命令。
   - 小步修改，结构性动作后做最小校验。
   - 遇到编码、命名、依赖、项目包含关系异常时先定位根因。
4. 主动验证：
   - 先跑语法、类型、编译或快检。
   - 再跑本次改动直接相关测试。
   - 用户可见行为变化需要运行级 smoke 或客观阻断说明。
5. 自审和交付：
   - 复查 diff 和工作树。
   - 说明改动、验证、未验证、剩余最小人工确认。
   - 需要收尾时更新进度、清理临时产物、提交。

## 4. 长期沉淀规则

1. 一次性约束放在当前任务或进度记录。
2. 长期硬规则放在 `AGENTS.md`，但只放每次都必须遵守的内容。
3. 专项知识放在 `docs/architecture/`、`docs/plans/` 或子目录文档。
4. 高频流程放成 `.agents/skills/`。
5. 必须机械执行的规则放成脚本、guard 或 hook。
6. 稳定验收标准沉淀为测试、smoke、eval 或检查脚本。
7. 失败第二次出现时，必须反向强化文档、skill、脚本或测试。

## 5. 差距自检

项目要定期检查：

1. Prompt 是否变短，但交付遗漏没有增加。
2. 同类任务人工纠偏次数是否下降。
3. 必要验证遗漏是否下降。
4. 无关文件改动是否下降。
5. 收尾说明是否稳定包含验证、提交、服务状态、部署状态、未验证原因和剩余手测。
6. 高风险任务是否不会绕过方案、人工确认、dry-run 或 smoke。

## 6. 暂不追求

1. 不追求全自动生产部署。
2. 不把 eval 当成业务测试替代品。
3. 不把所有历史文档迁移成 skills。
4. 不为了自动化放松密钥、权限、数据和上线门禁。
