# 验证矩阵

## 1. 当前最小入口

1. 项目初始化就绪：
   - `node scripts/check-project-ready.mjs`
2. Skill 基础结构：
   - `node scripts/check-skills.mjs`
3. 当前最小验证：
   - Android 工程建立前：`node scripts/check-project-ready.mjs`
   - Android 工程建立后：`./scripts/gradlew-jdk17.sh assembleDebug`；命中直接相关单测时追加对应测试
4. Debug APK 交付安装（不启动应用）：
   - `./scripts/install-debug-to-device.sh --install-only`
5. 运行级诊断（仅用户明确要求、里程碑或故障诊断时）：
   - `./scripts/install-debug-to-device.sh --runtime-smoke`

## 2. 分级

| 变更类型 | 必须验证 |
|---|---|
| 只读查询 | 不默认跑验证 |
| 文档、目录、模板底座 | `node scripts/check-project-ready.mjs`、`node scripts/check-skills.mjs`、`git diff --check` |
| Skill 新增或修改 | `node scripts/check-skills.mjs`、`git diff --check` |
| 代码或配置 | 语法 / 类型 / lint / 单测中最低成本可执行项 |
| 共享契约或跨模块逻辑 | 相关单测、集成测试、回归用例 |
| UI、启动、导航、输入、文件读写 | 直接相关机器检查 + 完整用户手测用例；不默认运行 smoke |
| 生产、数据、支付、账号、权限、密钥 | dry-run、相关测试、人工门禁、回滚说明 |
| 本轮车机 UI / 行车安全 | `assembleDebug` + 直接相关单测；需要交付 APK 时可 install-only；等待页、设置双栏、风险确认、档位状态、活动态关闭回等待、全屏活动态关闭回标准窗口由用户按手测清单验收 |

## 3. 协议探测入口

1. `./scripts/probe-dlna.sh`：从开发机发起 SSDP 搜索，验证描述、三项 SCPD 与基础 SOAP 控制。
2. `./scripts/probe-airplay.sh`：验证目标车机 TCP `7000`、`_raop._tcp` 与 `_airplay._tcp` 广播，不模拟受保护媒体会话。
3. 两个脚本均为只读探测，不安装、不授权、不修改车机设置。

## 4. V1 必须通过

1. 初始化与配置：项目就绪、技能、Android 配置、包名、最低版本、权限白名单和标准浮窗 metadata 检查通过。
2. 单元测试：状态机全部转换、跨协议接管、重复命令、断开、网络重绑和错误恢复通过。
3. DLNA 集成：SSDP 能发现“03投屏”，描述地址可访问，三项标准服务可查询，播放控制能映射到统一会话。
4. AirPlay 集成：mDNS 能发现“03投屏”，非 DRM 镜像与音频握手进入统一会话，断开能释放资源。
5. 媒体：目标车机硬件解码路径可启动，网络视频与镜像视频直接输出到不透明置顶 `SurfaceView`；普通 SDR H.264 在实体屏幕连续显示，活动视频层保持 `Device/HWC` 合成，音频焦点与画面表面正确获得和释放。
6. 运行级人工验收：由用户在 `S56_HQX` 上启动应用并完成标准浮窗 / 全屏边界、播放连续性、端口持续、歌词层避让和关闭释放；AI 不默认代替用户点击或截图。
7. 最小人工验收：真实 DLNA 发送端和 Apple 设备各完成一次发现、连接、播放 / 镜像、控制与断开恢复；硬件视频层以实体屏幕为画面真值，系统截图黑色不单独判失败；任一主路径失败由用户反馈后再进入针对性诊断。

## 5. 本轮 UI 与安全手测用例（用户执行）

前置条件：目标车机已安装 Debug APK；准备一个可发送 DLNA 媒体的手机和一个可发送 AirPlay 的 Apple 设备；行车档位用安全、合法的静止场景验证，不在行驶中操作。

1. 发现范围：打开应用并停留等待页，确认 Android / Apple 发送端能看到“03投屏”；下滑关闭窗口后，确认 `7000 / 8200 / 1900` 均不再监听。应用关闭期间不要求自动唤起。
2. 等待页：确认图标、设备名、等待文案垂直顺序；等待态没有关闭按钮；底部中央为文字“设置”按钮且可触控。
3. 设置页：确认左侧透明侧栏、标题与分类处于正常顶部位置、没有页内返回图标；右侧滚动内容可在 `投屏接收` / `播放安全` 间切换；行车保护默认开启。
4. 风险确认：点击关闭行车保护，确认出现应用内高风险遮罩；确认正文以“请确认由司机本人操作，乘客请勿点击”收尾，“扫码查看《03投屏用户协议》”位于二维码下方，按钮为“保持开启 / 仍要关闭”，且没有 Android 系统 Dialog。扫码确认 Debug 包打开 `https://staging.9studio.fun/icar03/terms`。
5. 档位状态：车辆保持 P 档时确认设置页显示 `P 档，允许播放`（目标车机的 `GEAR_SELECTION=11` 兼容值也应归入 P 档），且投屏不会触发行车安全退出；在安全静止条件下切到明确非 P 档后显示 `非 P 档，播放受限`。读取失败或异常编码只允许显示 `暂时无法读取车辆状态`，不修改车辆设置。
6. 非 P 档保护：在安全静止条件下切到非 P 档并开始投屏，确认画面和声音立即停止，提示背后为纯黑，显示“为了您的安全，行车状态下禁止播放”、5 秒倒计时并最终关闭窗口；倒计时期间发送端重复播放或重连也不得恢复画面和声音。
7. 会话与窗口：DLNA / AirPlay 播放中点击顶部关闭，确认只断开当前会话、页面回到等待且广播继续；用户在全屏活动态点击关闭时，确认主动回到标准浮窗等待态。发送端真正断开时，确认立即回到等待但保持当前窗口模式，不自动回浮窗、不等待 `2 s`；全屏等待态显示“退出全屏”按钮，点击后才回到标准浮窗。浮窗 -> 全屏应保持既有即时响应体感；全屏 -> 浮窗后进程继续存活、旧全屏窗口消失，且两个方向均不出现“无法切换窗口”类提示。服务尚未绑定时切换按钮不可操作，绑定后不得自动补执行旧点击。播放抖音短视频自动切换下一条时，确认 Stop / 重连不会触发窗口交接，下一条媒体可在当前窗口继续显示。
8. 播放控制：开始播放后静置约 3 秒，确认顶部结束投屏、左下播放键和底部时间轴同时隐藏；轻触画面后三者同时出现。验证放大后的图标、时间文字和进度拖动区易于触控，顶部与底部没有整条黑色遮罩；继续验证播放 / 暂停位置保持、未知时长禁用定位，以及镜像 / 图片隐藏不支持的控制。
9. 窗口互斥：从 03桌面打开其它标准浮窗，确认不与 03投屏重叠；全屏期间确认歌词层避让，退出后恢复。
10. 失败记录：任一步出现卡顿、闪退、黑屏、端口未释放或文案 / 布局错误，记录触发步骤、前后画面、发送端类型和时间，不继续扩大回归范围，交回 AI 做针对性诊断。
