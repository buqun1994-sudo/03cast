# V1 架构施工方案

## 1. 施工目标

1. 在 Android 9 `S56_HQX` 上交付独立应用“03投屏”，打开标准右侧浮窗后同时公开 DLNA 与 AirPlay；等待页、媒体控制、设置页和行车保护符合 iCAR 车机规范；播放中可在标准浮窗与全屏之间往返，活动态关闭回到等待，窗口关闭后停止接收。
2. DLNA 覆盖设备发现、设备描述、三项标准服务、SOAP 控制、GENA 订阅与网络媒体播放；AirPlay 覆盖非 DRM 镜像、音频和 URL / HLS 播放。
3. 两种协议共用一个会话状态机和一套媒体输出，任一时刻只允许一条活动会话。

## 2. 物理锚点

1. 应用入口：`app/src/main/java/com/ninepointnine/desktopcast/MainActivity.kt` 与 `FullscreenActivity.kt`，只负责窗口生命周期、视图渲染和用户动作转发；全屏入口在可见生命周期内持有 `FullDisplayOccupancyLeaseClient.kt` 的跨应用避让租约。
2. 窗口流程：`app/src/main/java/com/ninepointnine/desktopcast/window/CastWindowNavigator.kt` 负责公开任务 API、边界与失败恢复；`CastWindowHandoff.kt` 负责交接令牌和最长三秒的一次性完成动作，不接收任务 ID、`Activity`、`Context` 或其它 Android 字段。
3. 应用流程：`app/src/main/java/com/ninepointnine/desktopcast/session/CastSessionCoordinator.kt`，负责协议接管、状态转换、错误恢复、停止不变量与租约代次。
4. Android 服务：`app/src/main/java/com/ninepointnine/desktopcast/service/CastService.kt`，负责生命周期装配、网络观察与三秒窗口交接保护；`CastReceiverRuntime.kt` 负责协议监听、mDNS、native handle、唤醒锁和网络重绑。
5. 播放流程：`CastPlaybackRouter.kt` 是唯一共享网络播放器与会话接入点；`DlnaPlaybackAdapter.kt`、`AirPlayPlaybackAdapter.kt` 分别实现协议控制和原生回调，不能各自持有第二套会话状态机。
6. DLNA 适配器：`app/src/main/java/com/ninepointnine/desktopcast/dlna/`，负责 SSDP、HTTP、描述、SOAP 与 GENA，不持有界面引用。
7. AirPlay native：`app/src/main/java/com/ninepointnine/desktopcast/bridge/` 与 `app/src/main/cpp/`，基于固定上游源码快照；JNI 只传递协议事件、编码帧和播放状态。
8. 媒体输出：网络媒体由 `renderer/NetworkMediaPlayer.kt` 的 Media3 实现播放，镜像视频由 MediaCodec 输出，音频由原生低延迟输出处理；跨 Activity 窗口交接统一经过 `CastPlaybackRouter` 的媒体输出摘除确认和目标 renderer 输出确认，Android 9 厂商 codec 只允许释放 / 重建，不直接跨 BufferQueue 热切换。
9. 界面资源：`app/src/main/res/layout/activity_main.xml`、`values/`、`values-night/` 与 `anim/`；窗口主题和动画参数从 `/Users/q/Documents/Projects/03lyrics/app/src/main/res/values/themes.xml` 及同仓库 `anim/icar_standard_window_enter.xml`、`icar_standard_window_exit.xml` 取证。
10. 新增 Kotlin 文件头统一从本仓库 `app/src/main/java/com/ninepointnine/desktopcast/MainActivity.kt` 的 ASCII 包声明复制；包名固定 `com.ninepointnine.desktopcast`，UTF-8 编码。
11. UI 安全与设置锚点：`MainActivity.kt` 只负责 `ActivityMainBinding` 的页面状态和动作转发；`IcarSwitch.kt` 负责 64:36 物理开关绘制；`safety/DrivingSafetyPolicy.kt` 负责纯规则；`safety/IcarDrivingStateMonitor.kt` 负责只读 Automotive 档位适配。安全遮罩与媒体控制均通过同 Activity 的 attached `PopupWindow` 覆盖置顶 `SurfaceView`。

## 3. 核心流程与阈值

1. Activity 创建后绑定 `CastService`；服务先获得局域网 IPv4，再启动 AirPlay TCP 服务、严格串行注册 `_raop._tcp` 与 `_airplay._tcp`，同时启动 DLNA UDP `1900` 与 HTTP `8200`。
2. 等待态只显示设备名“03投屏”和“等待投屏”；连接建立后在 `CONNECTING` 最多停留 `15 s`，随后进入媒体、镜像或音频状态；可恢复错误提供一次“重试”。
3. 会话接管以单个同步入口完成：新发送端或新 URI 创建新租约，先停止旧媒体输出、通知旧协议断开并清空旧元数据；同一连接的轮询、音频格式、视频尺寸、进度和帧回调只复用当前租约，旧租约不得改写新状态。
4. DLNA HTTP 按字节读取 `Content-Length`，请求头上限 `64 KiB`，请求体上限 `2 MiB`，单连接读取超时 `15 s`；SOAP 使用 XML 解析器，不使用正则解析 XML。
5. GENA 订阅保存 `SID / callback / service / expiry / sequence`，默认 `1800 s`、最大 `86400 s`；状态、URI、播放位置跳变和音量变化时通知有效订阅。
6. SSDP 存活时间 `1800 s`，启动时连续广播两轮；回应 `M-SEARCH` 时只返回匹配目标并使用当前可访问描述地址。
7. 顶部结束投屏、底部播放和底部时间轴组成同一控制层：媒体轻触后同时显示，静置 `3 s` 后同时隐藏；音频态保持可见。媒体控件使用公开 Media3 `PlayerControlView` 接入既有播放 Router，底部不铺整条黑色遮罩；播放、全屏和结束投屏触控框统一为 `112dp x 112dp`，时间轴触控高为 `66dp`。
8. 网络 IPv4 发生变化时，先注销 mDNS、关闭 DLNA socket 与旧 HTTP 地址，再按新地址重新启动；相同地址的重复回调不重启。
9. 全屏交接：标准窗口进入全屏时先由 `CastService` 要求 `CastPlaybackRouter` 摘除旧媒体 Surface，并等待 Media3 播放线程确认 codec 已释放，再以 `NEW_TASK | MULTIPLE_TASK` 提交一次性全屏任务，不预先调用 `moveTaskToBack(true)`。`FullscreenActivity.onStart` 发现并绑定版本 `1` 的全屏独占 provider，`onStop` / `onDestroy` 释放。全屏返回时以 `NEW_TASK | REORDER_TO_FRONT` 复用或创建标准任务；目标启动调用成功后，必须先由目标完成对应输出 Surface 绑定，并由 renderer 确认同一 Surface 输出消息已处理后完成同一令牌，再由全屏 Activity 调用 `finishAndRemoveTask()`，后台不得保留全屏任务或视频层。目标启动失败才取消令牌、恢复仍存活来源的媒体输出并保留来源窗口；来源结束失败只记录诊断；服务不扫描或恢复任务；未绑定时切换控件不可用，三秒未确认只停止接收并释放交接资源。权益详情、关于页和两类协议二维码均不进入窗口创建主链，按首次打开对应界面加载。
10. UI 状态：等待态显示图标、设备名“03投屏”、等待文案和居中底部文字设置按钮；设置页分为“投屏接收 / 播放安全”两栏，不自带返回图标。活动态顶部关闭按钮只断开当前会话；用户主动点击全屏活动态关闭仍完成全屏 -> 标准窗口交接；发送端远程断开保持当前窗口模式并立即进入等待态，全屏等待态显示“退出全屏”按钮供用户主动回到标准浮窗。
11. 行车安全：保护默认开启；优先读标准 `CURRENT_GEAR`，目标 `S56_HQX` 在该字段无事件时回退到已取证的 `GEAR_SELECTION=11 -> P 档`兼容映射，明确非 P 档时先建立本次接收生命周期内不可逆的播放锁，释放视频、音频、镜像和图片输出，再显示纯黑背景上的 5 秒倒计时；倒计时结束停止服务并关闭本包全部任务。档位不可读或编码异常时显示不可用，不宣称允许或禁止。
12. 协议二维码：Debug 构建注入测试协议地址 `https://staging.9studio.fun/icar03/terms`，Release 构建注入正式协议地址 `https://9.9studio.fun/icar03/terms`；客户端本地生成二维码，版本号不参与环境判断。
13. 会话结束判定：媒体自然结束、DLNA Stop、AirPlay 视频 Stop / End 或协议权威的输出拆除到达时，Router 立即失效当前租约、释放媒体输出并转为 `WAITING`，发布 `REMOTE_DISCONNECTED`；该事件不得驱动窗口模式切换。通用 AirPlay 连接销毁只作为不抢占存活输出的幂等兜底。用户点击活动态关闭按钮走 `USER_REQUEST`，立即断开但保留两种协议广播。

## 4. 固定依赖与开源边界

1. AirPlay Android 接收器来源：`jqssun/android-airplay-server`，固定 commit `1fa1d609afdae9042be07ec430591339b8583e15`。
2. UxPlay 固定 commit `21eef8df25d91e12635c36d8176ad192725baca2`；libplist 固定 commit `f41b1ea67045e0c09339974d83e389972d84f166`；openssl-cmake 固定 commit `4edd36a8dab5f85a8f92650b5bdf6e0cab13aab8`。
3. 组合程序遵循 GPL-3.0；源码快照、许可证、补丁和来源说明必须随仓库保留。禁止删除 PlayFair、UxPlay、FFmpeg、libplist、OpenSSL 与 Oboe 的声明。
4. 不实现或宣称绕过 FairPlay / DRM；受保护内容失败属于明确产品边界。

## 5. 防守边界

1. 不加入 Compose、Hilt、设置页以外的历史记录、下载、媒体库、画中画、开机自启、退出后后台常驻或系统悬浮权限；本轮设置页只承载接收说明与行车保护。
2. 不依赖车厂私有媒体接口、系统签名、root、无障碍、ADB 运行时或外部转码服务器。
3. 不把协议解析、播放器状态或网络重绑逻辑放入 Activity。
4. 不修改 `/Users/q/Documents/Projects/03desktop`；`03lyrics` 只允许通过版本化全屏独占租约扩展其既有呈现策略，不接入投屏媒体、任务或窗口控制逻辑。

## 6. 测试闭环

1. 编译：普通切片默认执行 `./scripts/gradlew-jdk17.sh assembleDebug`；命中直接相关 JVM 单测时追加对应测试，不默认跑完整回归。
2. 单元测试：状态机全部转换、跨协议接管、重复命令、XML 参数解析、SOAP 响应、GENA 续订 / 退订、网络重绑与 mDNS 串行注册，按本轮直接影响范围选择执行；窗口媒体交接必须覆盖 Android 9 厂商 codec 重建策略、播放线程 detach acknowledgement、目标 renderer 对同一 Surface 的输出 acknowledgement、取消 / 超时来源输出恢复和同一 Holder 幂等绑定。
3. 本机协议探测：仅在本轮直接涉及协议发现 / 描述 / SOAP / mDNS 时执行；SSDP、描述和 SCPD 地址、基础 SOAP 与两种 mDNS 服务作为针对性机器检查，不作为每次 UI 切片的固定门禁。
4. APK 交付：需要把 Debug APK 放到目标车机时执行 `./scripts/install-debug-to-device.sh --install-only`，只覆盖安装、不启动、不代替用户验收；`--runtime-smoke` 仅在用户明确要求、里程碑或故障诊断时执行。
5. 用户手测：等待页设置入口、双栏导航、风险确认、档位状态、活动态关闭回等待、用户主动全屏活动态关闭回标准窗口、远程断开保持当前窗口模式、全屏等待态“退出全屏”按钮、普通 AVC 浮窗 -> 全屏 -> 浮窗、真实 DLNA / AirPlay 发现与断开恢复，按 `docs/testing/验证矩阵.md` 第 5 节完整用例由用户执行。
6. 失败反馈：用户报告卡顿、闪退、黑屏、端口未释放或协议失败后，AI 才针对触发步骤收集日志、复现和诊断；不把未执行的交互检查写成通过。

## 7. 次生风险

暂无明确次生风险。本项目尚无已实现的其它业务主链；协议接入不会回归既有用户功能。
