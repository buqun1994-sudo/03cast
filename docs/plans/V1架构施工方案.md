# V1 架构施工方案

## 1. 施工目标

1. 在 Android 9 `S56_HQX` 上交付独立应用“03投屏”，打开标准右侧浮窗后同时公开 DLNA 与 AirPlay；播放中可在标准浮窗与全屏之间往返，关闭窗口后停止接收。
2. DLNA 覆盖设备发现、设备描述、三项标准服务、SOAP 控制、GENA 订阅与网络媒体播放；AirPlay 覆盖非 DRM 镜像、音频和 URL / HLS 播放。
3. 两种协议共用一个会话状态机和一套媒体输出，任一时刻只允许一条活动会话。

## 2. 物理锚点

1. 应用入口：`app/src/main/java/com/tcrrry/desktopcast/MainActivity.kt` 与 `FullscreenActivity.kt`，只负责窗口生命周期、视图渲染和用户动作转发；全屏入口在可见生命周期内持有 `FullDisplayOccupancyLeaseClient.kt` 的跨应用避让租约。
2. 窗口流程：`app/src/main/java/com/tcrrry/desktopcast/window/CastWindowNavigator.kt` 负责公开任务 API、边界与失败恢复；`CastWindowHandoff.kt` 负责交接令牌，不持有 Android 对象。
3. 应用流程：`app/src/main/java/com/tcrrry/desktopcast/session/CastSessionCoordinator.kt`，负责协议接管、状态转换、错误恢复、停止不变量与租约代次。
4. Android 服务：`app/src/main/java/com/tcrrry/desktopcast/service/CastService.kt`，负责生命周期装配、网络观察与三秒窗口交接保护；`CastReceiverRuntime.kt` 负责协议监听、mDNS、native handle、唤醒锁和网络重绑。
5. 播放流程：`CastPlaybackRouter.kt` 是唯一共享网络播放器与会话接入点；`DlnaPlaybackAdapter.kt`、`AirPlayPlaybackAdapter.kt` 分别实现协议控制和原生回调，不能各自持有第二套会话状态机。
6. DLNA 适配器：`app/src/main/java/com/tcrrry/desktopcast/dlna/`，负责 SSDP、HTTP、描述、SOAP 与 GENA，不持有界面引用。
7. AirPlay native：`app/src/main/java/com/tcrrry/desktopcast/bridge/` 与 `app/src/main/cpp/`，基于固定上游源码快照；JNI 只传递协议事件、编码帧和播放状态。
8. 媒体输出：网络媒体由 `renderer/NetworkMediaPlayer.kt` 的 Media3 实现播放，镜像视频由 MediaCodec 输出，音频由原生低延迟输出处理。
9. 界面资源：`app/src/main/res/layout/activity_main.xml`、`values/`、`values-night/` 与 `anim/`；窗口主题和动画参数从 `/Users/q/Documents/Projects/03lyrics/app/src/main/res/values/themes.xml` 及同仓库 `anim/icar_standard_window_enter.xml`、`icar_standard_window_exit.xml` 取证。
10. 新增 Kotlin 文件头统一从本仓库 `app/src/main/java/com/tcrrry/desktopcast/MainActivity.kt` 的 ASCII 包声明复制；包名固定 `com.tcrrry.desktopcast`，UTF-8 编码。

## 3. 核心流程与阈值

1. Activity 创建后绑定 `CastService`；服务先获得局域网 IPv4，再启动 AirPlay TCP 服务、严格串行注册 `_raop._tcp` 与 `_airplay._tcp`，同时启动 DLNA UDP `1900` 与 HTTP `8200`。
2. 等待态只显示设备名“03投屏”和“等待投屏”；连接建立后在 `CONNECTING` 最多停留 `15 s`，随后进入媒体、镜像或音频状态；可恢复错误提供一次“重试”。
3. 会话接管以单个同步入口完成：新发送端或新 URI 创建新租约，先停止旧媒体输出、通知旧协议断开并清空旧元数据；同一连接的轮询、音频格式、视频尺寸、进度和帧回调只复用当前租约，旧租约不得改写新状态。
4. DLNA HTTP 按字节读取 `Content-Length`，请求头上限 `64 KiB`，请求体上限 `2 MiB`，单连接读取超时 `15 s`；SOAP 使用 XML 解析器，不使用正则解析 XML。
5. GENA 订阅保存 `SID / callback / service / expiry / sequence`，默认 `1800 s`、最大 `86400 s`；状态、URI、播放位置跳变和音量变化时通知有效订阅。
6. SSDP 存活时间 `1800 s`，启动时连续广播两轮；回应 `M-SEARCH` 时只返回匹配目标并使用当前可访问描述地址。
7. 播放控件在媒体轻触后显示，静置 `3 s` 隐藏；镜像状态只保留结束投屏动作。所有触控目标不小于 `54 dp`。
8. 网络 IPv4 发生变化时，先注销 mDNS、关闭 DLNA socket 与旧 HTTP 地址，再按新地址重新启动；相同地址的重复回调不重启。
9. 全屏交接：标准窗口进入全屏时先取得服务交接令牌、将原标准任务放后台、启动独立全屏任务；`FullscreenActivity.onStart` 发现并绑定版本 `1` 的全屏独占 provider，`onStop` / `onDestroy` 释放。全屏返回时以 `REORDER_TO_FRONT` 复用或重建标准任务并结束全屏任务。目标 Activity 只有持有相同令牌时才能完成交接；三秒内未完成则服务停止接收，失败时恢复原任务。

## 4. 固定依赖与开源边界

1. AirPlay Android 接收器来源：`jqssun/android-airplay-server`，固定 commit `1fa1d609afdae9042be07ec430591339b8583e15`。
2. UxPlay 固定 commit `21eef8df25d91e12635c36d8176ad192725baca2`；libplist 固定 commit `f41b1ea67045e0c09339974d83e389972d84f166`；openssl-cmake 固定 commit `4edd36a8dab5f85a8f92650b5bdf6e0cab13aab8`。
3. 组合程序遵循 GPL-3.0；源码快照、许可证、补丁和来源说明必须随仓库保留。禁止删除 PlayFair、UxPlay、FFmpeg、libplist、OpenSSL 与 Oboe 的声明。
4. 不实现或宣称绕过 FairPlay / DRM；受保护内容失败属于明确产品边界。

## 5. 防守边界

1. 不加入 Compose、Hilt、设置页、历史记录、下载、媒体库、画中画、开机自启、退出后后台常驻或系统悬浮权限。
2. 不依赖车厂私有媒体接口、系统签名、root、无障碍、ADB 运行时或外部转码服务器。
3. 不把协议解析、播放器状态或网络重绑逻辑放入 Activity。
4. 不修改 `/Users/q/Documents/Projects/03desktop`；`03lyrics` 只允许通过版本化全屏独占租约扩展其既有呈现策略，不接入投屏媒体、任务或窗口控制逻辑。

## 6. 测试闭环

1. 编译：`./scripts/gradlew-jdk17.sh testDebugUnitTest assembleDebug` 必须通过。
2. 单元测试：状态机全部转换、跨协议接管、重复命令、XML 参数解析、SOAP 响应、GENA 续订 / 退订、网络重绑与 mDNS 串行注册必须通过。
3. 本机协议探测：SSDP 能找到“03投屏”，描述和 SCPD 地址可访问，SOAP 可设置 URI 并查询状态；mDNS 同时出现 `_raop._tcp` 与 `_airplay._tcp`。
4. 车机运行级：覆盖安装后 Activity、进程和接收服务正常；普通 AVC 播放中完成浮窗 -> 全屏 -> 浮窗，边界依次为 `(660, 90) .. (1890, 900)`、`(0, 0) .. (1920, 1080)`、`(660, 90) .. (1890, 900)`，播放和端口持续；关闭后 TCP `7000`、HTTP `8200` 与 UDP `1900` 释放。
5. 剩余人工确认：真实 DLNA 发送端与 Apple 设备各完成一次发现、首帧、声画、控制和断开恢复。上述任一“必须通过”项失败即不达标。

## 7. 次生风险

暂无明确次生风险。本项目尚无已实现的其它业务主链；协议接入不会回归既有用户功能。
